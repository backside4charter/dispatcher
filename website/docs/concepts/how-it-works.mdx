# How it works

<p className="lede">
You keep a task board in Linear. The dispatcher is a Claude Code session you
start with <code>/dispatcher:start &lt;milestone&gt;</code>. It moves each card
from Ready to Human Review with agents doing the work in between. You decide
what is ready, and you merge.
</p>

<Diagram flow={howItWorks} caption="The board's columns in its own colours. Solid arrows are the main flow; dashed arrows are the two detours.">
  <Stage id="backlog" title="Backlog" k="you decide">

Nothing here is touched by the dispatcher. Move a task to Ready when you want
it built.

[The board →](the-board.md)

  </Stage>
  <Stage id="ready" title="Ready" k="you decide">

Agent-workable and never worked. The dispatcher takes the topmost Ready task
in the milestones you named, so board order is the priority. A `Confirm with
user` label or an open blocker keeps it waiting.

[What makes a task eligible →](../ai/system.md#eligibility)

  </Stage>
  <Stage id="in-progress" title="In Progress" k="agents · build, then review">

A developer agent lands the task as one pull request, then a reviewer agent
checks it and posts its findings on the PR. A pass moves the task on to you;
problems send it back; a decision only you can make parks it as a Question.

[Inside In Progress →](#inside-in-progress)

  </Stage>
  <Stage id="human-review" title="Human Review" k="your review">

The agents are done and the PR is yours. Merge it, or request changes on the
PR and the task goes back to the developer within seconds, with your review
carried into its instructions word for word.

[Review sync →](../setup/review-sync.md)

  </Stage>
  <Stage id="done" title="Done" k="your merge">

Your merge completes the task through Linear's GitHub integration. No agent
ever merges or marks a task Done.

[The GitHub integration →](../setup/linear.md#6-the-github-integration)

  </Stage>
  <Stage id="changes-requested" title="Changes Requested" k="detour · sent back">

Rework, not a restart: the same pull request gets more commits from the next
developer, and it jumps ahead of every Ready task.

[Rework →](../ai/system.md#rework)

  </Stage>
  <Stage id="question" title="Question" k="detour · waiting on you">

An agent met a decision only you can make and stopped rather than guess. The
question is a comment on the issue. Reply there and move the task to Ready
(nothing built yet) or Changes Requested (a PR exists).

[Questions →](../ai/system.md#questions)

  </Stage>
</Diagram>

A card moves left to right. You put it in `Ready`; the agents take it through
`In Progress`; when the review passes it lands in `Human Review`; your merge
moves it to `Done`. Problems found in review, or changes you request, send it
back to `Changes Requested`. A question for you parks it in `Question`.

## Inside In Progress

<Diagram flow={agentsAtWork} caption="Each step names who does it. Solid arrows are the round every task takes; dashed arrows are the returns.">
  <Stage id="claim" title="Claim and spawn" k="dispatcher">

The dispatcher takes the topmost eligible task, marks it as claimed so no
other session takes it, and starts a developer agent with instructions built
from the issue.

[The loop in detail →](../ai/system.md#the-loop)

  </Stage>
  <Stage id="build" title="Build one PR" k="developer agent">

In its own working copy the developer builds the task as one branch and one
pull request, ticking the issue's checklist as pieces land. A task that was
sent back resumes its existing PR.

[The developer →](../ai/system.md#developer)

  </Stage>
  <Stage id="verify" title="Verify, don't trust" k="dispatcher">

Before anything moves, the dispatcher checks GitHub: the PR exists, the
checks are green, every box on the checklist is ticked. A report that does
not hold up gets one retry, then is flagged to you.

[Routing a developer's result →](../ai/system.md#routing-a-developers-result)

  </Stage>
  <Stage id="review" title="Review the PR" k="reviewer agent">

A read-only reviewer hunts for real flaws and leaves its findings on the PR,
line by line. It ends with a pass, a send-back, or a question for you. There
is no limit on review rounds.

[The reviewer →](../ai/system.md#reviewer)

  </Stage>
  <Stage id="human-review" title="Human Review" k="you">

The PR is yours to read. Merge it, or request changes and the task goes back
to the developer.

[Review sync →](../setup/review-sync.md)

  </Stage>
  <Stage id="clean" title="Resolve conflicts" k="cleaner agent">

While a PR waits for you, the dispatcher keeps it up to date with `main`. One
that no longer merges cleanly goes to the cleaner, which resolves the
conflicts without changing what the PR does and hands it back.

[The cleaner →](../ai/system.md#cleaner)

  </Stage>
</Diagram>

## What stays yours

- Deciding what is ready: moving a task from `Backlog` to `Ready`.
- Priority: the board's manual order is the only ranking.
- Answering the questions an agent could not decide alone.
- Reviewing and merging. Your merge is what marks a task `Done`.
- Anything you want to build yourself: assign yourself with no agent, and the
  dispatcher leaves that task alone ([how](the-board.md#taking-a-task-yourself)).

Stop the loop at any time with `/dispatcher:stop`. Everything that matters is
on the board and on GitHub, so the next start resumes where it left off.

## Why it is safe to leave running

- Agent commits and PRs are made by a **developer GitHub App** and reviews by
  a separate **reviewer app**, so GitHub lets you approve every PR and no
  agent can approve anything.
- A worker's report is **checked against GitHub** before the board moves.
- Nothing hidden lives in the session: claims, states and PRs are all
  **visible on the board and in the repository**.
